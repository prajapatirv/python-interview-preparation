### Q1 [basic] What makes an API RESTful?
Resources identified by URLs (`/orders/42`), standard HTTP verbs, stateless requests, representations (JSON), correct status codes, cacheability, and (ideally) hypermedia. Nouns in URLs, verbs in HTTP methods.

### Q2 [basic] GET vs POST vs PUT vs PATCH vs DELETE - which are safe and idempotent?
Safe (no change): GET, HEAD. Idempotent (same result if repeated): GET, PUT, DELETE, HEAD. POST is neither; PATCH is not guaranteed idempotent. PUT replaces the whole resource; PATCH changes part of it.

### Q3 [basic] Which status codes do you use and when?
200 OK, 201 Created (+`Location`), 202 Accepted (async), 204 No Content, 400 bad input, 401 not authenticated, 403 not allowed, 404 not found, 409 conflict (version/duplicate), 422 semantic validation, 429 too many requests, 500 server bug, 502/503/504 upstream problems. Never return 200 with an error inside.

### Q4 [intermediate] How do you make a POST idempotent (e.g. payment/order creation)?
Client sends an `Idempotency-Key` header. Server stores `key -> request hash -> response` (unique constraint) in the same transaction as the business write; a repeat returns the stored response; same key with a different body returns 409/422. Keys expire after ~24h. This is what makes retries safe.

### Q5 [intermediate] How do you version an API?
Options: URL (`/v2/orders`), header/media type (`Accept: application/vnd.app.v2+json`), query param. URL versioning is the most visible and simplest for consumers; Spring Framework 7 now has built-in versioning support. Policy matters more than mechanism: only version for breaking changes, add fields compatibly, publish a deprecation date, support N-1.

### Q6 [intermediate] How do you design pagination, filtering and sorting?
`GET /orders?status=PAID&sort=-createdAt&limit=50&cursor=abc`. Offset/limit is simple but slow and unstable on large/changing data; **cursor (keyset)** pagination is stable and fast. Return `nextCursor` and a total only if it's cheap. Cap `limit`; whitelist sortable fields.

### Q7 [intermediate] How do you design the error response?
One consistent shape (RFC 7807 Problem Details): `type`, `title`, `status`, `detail`, `instance`, plus `code` and `errors[]` for field problems and a `traceId` for support. Stable machine codes, human text, no stack traces.

### Q8 [intermediate] PUT vs PATCH and optimistic concurrency over HTTP?
Use `ETag`/`If-Match` (or a `version` field): the client sends the version it read; the server returns `412 Precondition Failed` (or 409) if it changed - prevents lost updates in concurrent edits.

### Q9 [intermediate] How do you handle long-running operations?
Return `202 Accepted` with `Location: /jobs/123`; the client polls `GET /jobs/123` (status, progress, result link) or receives a webhook/event. Persist the job, make the worker idempotent, expire results. Good example: the large file upload pipeline.

### Q10 [intermediate] How do you handle large file upload/download?
Don't stream large files through the service if you can avoid it: return a **pre-signed URL** so the client uploads directly to S3/Blob storage, using **multipart upload** (parallel parts, resume on failure), then notify the service (event). Validate size/type, scan for malware, and use `Range` requests for downloads.

### Q11 [intermediate] REST vs GraphQL vs gRPC?
REST: simple, cacheable, universal. GraphQL: flexible client-chosen fields, avoids over/under-fetching, but needs query cost limits and is harder to cache. gRPC: binary Protobuf over HTTP/2, strongly typed, streaming, best for internal service-to-service. Typical choice: REST for public, gRPC internal, GraphQL for a BFF over many backends.

### Q12 [intermediate] How do you secure a REST API?
TLS everywhere, OAuth2/JWT, least-privilege scopes, object-level authorization (IDOR checks), input validation, rate limiting, request size limits, CORS allow-list, no secrets in URLs, audit logs, and an API gateway/WAF in front. Return 404 vs 403 deliberately for resources the caller must not know exist.

### Q13 [intermediate] What is HATEOAS and do you use it?
Responses include links to the next possible actions. It's the "full REST" maturity level; in practice few teams use it - clear documentation and stable URLs matter more. Be honest: "I know it, I use it only where clients really are generic".

### Q14 [advanced] How do you document and test the contract?
OpenAPI spec (design-first or generated by springdoc), published to a portal; **consumer-driven contract tests** (Pact / Spring Cloud Contract) so a provider can't break a consumer; schema/breaking-change checks (openapi-diff) in CI; mock servers for parallel development.

### Q15 [advanced] How do you make API calls to other services resilient?
Always set connect and read **timeouts**; retry only idempotent calls with exponential backoff + jitter and a cap; **circuit breaker** to stop hammering a failing service; **bulkhead** to isolate pools; fallback/cached response where acceptable; propagate a deadline so downstream doesn't work for a caller that already gave up. (Resilience4j or Spring Framework 7 `@Retryable`/`@ConcurrencyLimit`.)

### Q16 [advanced] Compression, caching and performance tips?
Enable gzip/br for JSON, HTTP caching (`Cache-Control`, `ETag`, 304), pagination, field selection, avoid chatty APIs (batch endpoints), connection reuse (HTTP keep-alive/HTTP2), asynchronous processing for slow work, and measure p95/p99 per endpoint.

### Q17 [intermediate] What is a webhook and how do you make it reliable?
The server calls the client's URL on an event. Reliability: sign payloads (HMAC), retries with backoff, idempotent event ids, a delivery log and replay endpoint, a dead-letter list, and timeouts on the receiver. Treat the receiver as unreliable.

### Q18 [design] Design a public "Orders" API for 3rd-party partners.
Resources: `/orders`, `/orders/{id}`, `/orders/{id}/payments`. Auth: OAuth2 client credentials + per-partner rate limits via gateway. Writes: idempotency keys, optimistic version. Reads: cursor pagination, filtering, ETag caching. Errors: Problem Details. Evolution: URL major version, additive changes only, changelog, sandbox environment. Observability: per-partner dashboards, request ids, SLOs, usage metering. Async events: webhooks with signing.

### Q19 [design] Design an API gateway layer. What belongs there and what does not?
Belongs: TLS termination, authentication, coarse authorization, rate limiting, routing, request/response logging, CORS, caching of public GETs, canary routing. Does **not** belong: business logic, data orchestration across many domains (use a BFF/aggregator service), heavy transformations. Make it highly available and observable; keep config in Git.

### Q20 [intermediate] How do you deprecate an endpoint without breaking clients?
Announce with a date, add `Deprecation`/`Sunset` headers, log which clients still call it (by API key), contact heavy users, run both versions, and remove only when usage is ~zero. Metrics decide the removal date.

### Q21 [design] Design the versioning and deprecation strategy for an API with 200 external consumers.
Prefer additive, backward-compatible changes (new optional fields, new endpoints) so most changes need no new version. For breaking changes use a URI or header version, publish an OpenAPI contract, run consumer-driven contract tests, and announce deprecation with `Deprecation`/`Sunset` headers and usage metrics per consumer. Keep at most two live versions and give a dated sunset. Failure mode: silently removing a field a consumer relies on - detect with traffic analysis before cutting off.
